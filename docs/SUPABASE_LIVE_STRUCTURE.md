# فحص البنية الحية لـSupabase — 2026-10-30

## نتيجة الفحص المباشر

أُجري فحص **قراءة فقط** لبيانات المشروع النشط المرتبط بالمنصة في Supabase بتاريخ **30 أكتوبر 2026**. شمل الفحص بنية الجداول والأعمدة والقيود وسياسات `RLS` والفهارس والروتينات ومشغّل الحدث. هذا وصف للـmetadata الحية وقت الفحص، وليس استنتاجًا من ملف المصدر.

### الجداول العامة وسياسات RLS

ظهرت أربعة جداول عامة، وكلها مفعّل عليها `RLS`:

**`bayyena_knowledge`** — العمود المتجهي `vector(1536)` ومفتاحه الأساسي `chunk_id`. له فهرس `HNSW` للتشابه الكوسايني. لم تُظهر نتيجة فحص السياسات العامة أي policy عامة لهذا الجدول؛ ولا يُستنتج من ذلك وحده أسلوب وصول الخدمات ذات الامتيازات الأعلى.

**`history`** — المفتاح الأساسي `id`، و`user_id` مفتاح أجنبي إلى `auth.users(id)` مع `ON DELETE CASCADE`. قيد `kind` يقبل `review` و`draft` و`research` و`chat`. ظهرت سياسات للمستخدم المصادق لإضافة وقراءة وحذف صفوفه، مع قصر `user_id` على `auth.uid()`.

**`review_jobs`** — المفتاح الأساسي `id`، و`user_id` مفتاح أجنبي إلى `auth.users(id)` مع `ON DELETE CASCADE`. سياسات الإدخال والقراءة والتحديث تقيد الصفوف بهوية `auth.uid()`.

**`support_tickets`** — المفتاح الأساسي `id`، و`user_id` مفتاح أجنبي إلى `auth.users(id)` مع `ON DELETE CASCADE`. قيد الحالة يقبل `open` و`in_progress` و`resolved` و`closed`. سياسة الإدخال الذاتي تشترط الحالة `open` وأن يكون `admin_reply` و`ai_analysis` فارغين، مع سياسة قراءة لصفوف صاحبها.

يلخص هذا التقرير أهم المفاتيح والقيود والسياسات التي وردت في نتائج الفحص؛ لا يسرد كل عمود أو يعيد نشر نصوص جميع السياسات كاملة.

### الفهارس والروتينات ومشغّل الحدث

- `history_user_idx` على `(user_id, created_at DESC)`.
- `bayyena_knowledge_emb_idx` فهرس `HNSW` يستخدم `vector_cosine_ops`.
- `match_bayyena_knowledge`: روتين SQL للبحث بالتشابه، بحد أقصى 12 نتيجة.
- `rls_auto_enable`: روتين عام من نوع event-trigger function.
- `ensure_rls`: مشغّل حدث معرّف من المستخدم يعمل بعد `ddl_command_end` على tags `CREATE TABLE` و`CREATE TABLE AS` و`SELECT INTO`، ويستدعي `rls_auto_enable()`.

ظهرت أيضًا مشغلات أحداث تديرها Supabase؛ لم تُستخرج تعريفاتها ولم تُعدّل أو تُستبدل.

## ما لم يثبته الفحص

أعاد استدعاء `list_migrations` قائمة فارغة. هذا يثبت فقط أن الاستدعاء لم يعرض سجلات ترحيل؛ ولا يثبت عدم وجود تاريخ في مصدر آخر أو سجل نشر كامل.

الفحص وصفي للـmetadata: لم تُقرأ أو تُصدّر قيم صفوف، ولم يُطبّق أي `SQL`. كما لم تُختبر سياسات RLS بمحاولات وصول فعلية من جلسات `anon` أو مستخدمين مختلفين، ولم يُختبر أداء الدوال. لا يُعد هذا التقرير ملف DDL كاملًا أو SQL قابلًا لإعادة التشغيل.

## العلاقة بملفات المصدر

`database/01-schema.sql` مسودة SQL تاريخية معاد بناؤها، وليست البنية الحية التي عوينت مباشرة، ولا snapshot SQL أو migration. أُبقيت منفصلة عن ملخص metadata الحية. لا ندّعي سجل ترحيلات كاملًا أو migration نشر قابلة لإعادة التشغيل. يلزم مصدر schema موثوق ومراجعة التعريفات كاملة وإعداد migration منفصلة ومختبرة بموافقة مالك المشروع؛ لم يُنشأ أو يُطبّق أي migration هنا.

## ما يلزم لإغلاق الفجوة (7b)

قبل إعداد migration قابلة لإعادة التشغيل، يلزم من مالك المشروع مصدر معتمد وكامل لتعريف القاعدة وسجل التغييرات المتاح، بما يشمل الجداول والأعمدة والقيود والفهارس والمنح وسياسات RLS والدوال والمشغلات والامتدادات. ملخص metadata الوصفي في هذا المستند لا يكفي لاشتقاق DDL موثوق؛ لذلك لم يُنشأ SQL جديد ولم يُعدّل أي ملف SQL.

يلزم بعد ذلك اختبار migration في مشروع مرحلي منفصل وبموافقة المالك قبل التفكير في أي تطبيق على قاعدة حية. ويجب توثيق اختبارات RLS بجلسات `anon` وحسابين تجريبيين منفصلين على الأقل، تشمل الوصول إلى صفوف المالك مقابل رفض الوصول المتبادل، والعمليات المسموح بها لكل جدول، وحدود صلاحيات مسارات المعرفة والدعم. لم تُنشأ جلسات أو بيانات اختبار ولم تُنفذ هذه الخطوات في هذه الحزمة.
